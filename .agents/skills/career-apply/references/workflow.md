# JD workflow

Follow the rules in [AGENTS.md](../../../../AGENTS.md) and the sibling [evidence policy](evidence-policy.md) and [quality gates](quality-gates.md). Use the canonical local data for a real candidate, never the synthetic examples.

1. Save the supplied JD in `applications/<slug>/_work/jd.txt` (slug from the vacancy; avoid overwriting earlier work). If it is a URL, record source and retrieval date. Research the vacancy from its original page and official organization sources when available; distinguish verified information from inference. Research may shape positioning, not candidate history.
2. `uv run career validate`, `uv run career facts --json`, and `uv run career match applications/<slug>/_work/jd.txt --json`. Inspect all experiences and relevant profile education. `match` is lexical only. Record a requirement→fact-ID map with direct, transferable, or gap status; record reasons for significant exclusions.
3. For material gaps, ask once whether the user has undocumented experience before drafting. If they have none or choose to proceed, retain the gaps. If they provide new facts, inspect the existing experience YAML; use `uv run career add <experience_id> --text '...' --stage`, `uv run career validate --staging`, show a diff of the staged additions and compare them to canonical facts (staging is proposals only), then wait for explicit approval of the **entire staging file**. `career promote` appends all staged facts; if only a subset is approved, prepare an approved-only staging proposal, revalidate and show that revised diff for confirmation. Re-read the full staging file immediately before promotion. Only after it exactly matches the approved set, promote and rerun `uv run career validate` and the evidence map. Never use unapproved facts.
4. Select fact IDs, then create the spec skeleton: `uv run career build --include <id1>,<id2> --output applications/<slug>/_work/resume.yaml`. Edit `name` to a filename stem and set `target.company` and `target.role` truthfully; add education IDs if relevant. Empty `bullet.text` means the renderer uses canonical text. If rewriting bullets, keep their `source_fact_ids` and all metric values; the JD is not permission to invent claims. Keep a gaps file with `GAPS`, `TRANSFERABLE` (bounded wording and IDs), `STRENGTHS` (IDs).
5. Validate and review the final spec, then render using [quality gates](quality-gates.md). The CLI prints `generated/<name>.pdf`; copy it into the application folder only after checking it. An optional stretched spec must still obey [evidence policy](evidence-policy.md); unsupported study or adjacent experience belongs in a separate learning note, not in a resume.

For a runnable exercise using only fictional evidence, follow [the user guide](../../../../docs/USER_GUIDE.md). Do not try to load unrelated reference repositories or removed documentation.
